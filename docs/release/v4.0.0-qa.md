# v4.0.0 final QA plan

This is the last gate before the `v4.0.0` and `train-1` tags. The release's scope and exit
criteria are in the release ticket,
[ECO-5](https://linear.app/econgraph/issue/ECO-5).

CI proves the release against recorded fixtures only, and no live API key is present anywhere in CI.
This phase deploys the release candidate with real credentials and checks what fixtures
can't: live source coverage, seven days of scheduled refresh, sign-in through the real Keycloak and Google,
and the end-to-end suite against the deployed URL. It covers exit criteria 2, 3, 5 and 6 in
ECO-5. Criterion 1 is covered by tagging the exact commit QA tested.

## Before QA starts

QA runs on a release branch (see the [release process](../development/RELEASE_PROCESS.md)).
Once every item in the release is merged and CI is green on `main`, `release/v4.0` is cut from
that commit. The rest of this list is checked on the branch head, which is the release
candidate. The release candidate images, QA fixes and the tag all live on that branch, and
`main` reopens for later work. Fixes land on the branch first and are forward-ported to `main`.

- Every item in the release is merged and CI is green on `main`; `release/v4.0` is cut from that commit.
- Core CI and the `Release E2E` workflow (`.github/workflows/release-e2e.yml`) run on pull
  requests into any branch, including `release/**`. Core CI skips only Markdown and `docs/` changes;
  `Release E2E` runs only for changes under `frontend/`, `backend/`, `scripts/release-e2e.sh`
  or its own workflow file. A manifest-only fix therefore gets Core CI but not Release E2E, and
  a docs-only fix gets neither.
- A manual (`workflow_dispatch`) run of the `Release E2E` workflow passes on the release candidate commit.
- The nothing-fake check (`scripts/check-release-features.sh` and
  `frontend/scripts/check-release-authenticity.mjs`) passes with an empty allowlist.
- The GraphQL operation skip list (`frontend/src/__tests__/graphqlOperationSkipList.ts`, PR #208) holds
  no operation used by a reachable route.
- The release image workflow (`.github/workflows/release.yml`) can run by `workflow_dispatch` on a commit, and on a `v4.0.0-rc.N`
  tag, and builds the backend, crawler-worker and frontend images tagged with the commit SHA.
  QA deploys those images; the QA log records the SHA. The final tag step reuses their digests
  rather than rebuilding them.
- The Release E2E suite has a deployed-URL mode, set by `RELEASE_BASE_URL`
  (`frontend/tests/e2e/release/env.ts`). It skips the local `webServer`, needs no database URL,
  switches to the live assertions in check 3, and takes the QA test users' passwords from the
  environment.
- The QA-only test users exist in the QA realm. Their definitions (`qa-alice`, `qa-bob`) are in
  `config/keycloak/qa/` and are imported only through `docker-compose.qa-users.yml`; nothing in
  `k8s/` may reference them (`scripts/keycloak/check-no-dev-users-in-k8s.sh` fails CI if it
  does), so on a cluster a QA step creates the two users with `kcadm` or the admin API. Direct
  grants are off in the deployed realm, so the suite signs in through the browser form.
- The new Google OAuth client exists and its id and secret are in the Keycloak Secret before
  Keycloak's first start (see "Credentials and deploy config"), and the leaked Google client
  and Facebook app are revoked (check 5 confirms it).

## The target

This plan doesn't fix where `v4.0.0` runs. Whatever the target, it needs these pieces:

- the backend, the frontend, the crawler-worker, Postgres 18 and Keycloak;
- Prometheus loading `k8s/monitoring/prometheus-rules-crawler.yaml`, because criterion 3 is an
  alert firing in Prometheus.

The repo's Kubernetes path (`scripts/deploy/deploy.sh` with `k8s/manifests`) has all of these.
The commands below assume it; a different target needs equivalent commands. Things to know
about that path:

- `deploy.sh` also applies and waits for the chart API, which `v4.0.0` doesn't
  ship. Skip that manifest, or accept that it runs whatever image it names.
  It does not deploy the admin frontend.
- The manifests name fixed image tags. The release candidate deploy sets the backend,
  crawler-worker and frontend images to the SHA tags the release image workflow built (`kubectl set image`, or an
  edited copy of the manifests), and the QA log records that SHA.
- The Keycloak manifests carry `localhost` literals: `KC_HOSTNAME`, `KC_HOSTNAME_ADMIN` and
  `KC_WEB_BASE_URL` in `k8s/manifests/keycloak/deployment.yaml` and the ingress hosts in
  `k8s/manifests/keycloak/ingress.yaml` and `k8s/manifests/ingress.yaml` (frontend and backend,
  the same domain `CORS_ORIGIN` names) are edited together for the real domain, like the image
  tags. The settings table below gives the values.
- Only the cluster that serves the public site is marked production: run
  `scripts/deploy/mark-production-cluster.sh` on it once after creating it, and again after
  every recreate, before deploying with `PUBLIC_HOST` or entering the tunnel token
  (`scripts/deploy/create-secrets.sh --prompt-tunnel-token`). All three use
  `${KUBECTL:-kubectl}` on its current context; where plain `kubectl` is another cluster's
  (the microk8s snap wrapper), set `KUBECTL` and `KUBECONFIG` to the production cluster's
  kubectl and kubeconfig for each of them. Without the marker,
  `create-secrets.sh` refuses the token and `deploy.sh` never starts cloudflared: with
  `PUBLIC_HOST=` (empty) it scales it to 0, and with a non-empty `PUBLIC_HOST` it stops before
  applying anything, so a connector started earlier keeps running there. A QA or test
  cluster is never marked and never gets the token: every cloudflared running with it
  silently takes a share of the public site's traffic. See "Production marker" in
  `k8s/README.md`.
- Once on every cluster that is not production, including any that held the token before
  the marker existed, run `scripts/deploy/mark-production-cluster.sh --unmark`. It scales
  cloudflared to 0 and offers to delete the Secret `cloudflare-tunnel`; type `delete` to
  delete it.

## Credentials and deploy config

Each credential lives in a Secret (created by `scripts/deploy/create-secrets.sh`, SEC-FIX-3) or
in the target's equivalent. No credential goes in the repo or in `k8s/manifests/configmap.yaml`.

| Credential | Used by | Notes |
|---|---|---|
| `FRED_API_KEY` | crawler | required |
| `BEA_API_KEY` | crawler | required |
| `CENSUS_API_KEY` | crawler | required for Census BDS |
| `BLS_API_KEY` | crawler | optional, but it raises the BLS limits the widened series list needs |
| Google OAuth client id and secret | Keycloak Google identity provider | a new client, created after the leaked one is revoked (check 5). It must be in the Secret (keys `google-idp-client-id` and `google-idp-client-secret`) before Keycloak's first start: the realm import reads it once, and after that it is changed only in the Keycloak admin console |
| QA test users (two realm-local users with passwords) | Keycloak, QA only | see "Before QA starts": created by a QA-only import behind a switch that is off by default, or by hand with `kcadm`; never in production. They let check 3 run the two-account annotation check automatically |
| Keycloak admin and database passwords | Keycloak | Secret `econ-graph-keycloak` |
| Database password | backend, crawler | |

FHFA and the World Bank need no key.

| Setting | Value |
|---|---|
| `vars.VITE_OIDC_ISSUER` (repository variable, frontend build) | `https://<keycloak-host>/idp/realms/econ-graph` (PR #236 serves Keycloak under `KC_HTTP_RELATIVE_PATH=/idp`; drop `/idp` on a target that doesn't). If unset, the build hides sign-in, so it must be set before the release candidate build |
| `vars.VITE_OIDC_CLIENT_ID` | only if the client isn't `econ-graph-web` (the default) |
| Backend `OIDC_ISSUER` | exactly the same string as `vars.VITE_OIDC_ISSUER`, since the backend compares `iss` exactly. It is set inline in `k8s/manifests/backend-deployment.yaml` (AUTH-5, PR #261) rather than in the configmap, and the manifest's value is the kind one, `http://localhost/idp/realms/econ-graph`. It must equal Keycloak's `KC_HOSTNAME` plus `/realms/econ-graph`, so change the two together |
| Backend `OIDC_JWKS_URL` | keep the in-cluster `keycloak-service` URL from `backend-deployment.yaml`, so the backend fetches signing keys without going through the public ingress. Clear it only if the backend can reach the public issuer URL |
| Backend `OIDC_AUDIENCE` | `econ-graph-api`, as the manifest already sets it (also the default) |
| `CORS_ORIGIN` (configmap, feeds `CORS_ALLOWED_ORIGINS`) | the deployed frontend origin, not `http://localhost:3000` |
| Keycloak `KC_HOSTNAME` | the public Keycloak URL, including `/idp` on the Kubernetes path |
| Keycloak `KC_HOSTNAME_ADMIN` | the admin console URL on the real domain, or remove the variable so the admin console shares `KC_HOSTNAME` (the manifest's value is a kind port-forward URL) |
| Keycloak `KC_WEB_BASE_URL` | the deployed frontend origin (the same value as `CORS_ORIGIN`): the realm's `econ-graph-web` client takes its root URL, redirect URIs and web origins from it |
| Google client's redirect URI | `https://<keycloak-host>/idp/realms/econ-graph/broker/google/endpoint` |
| Keycloak ingress host and CSP | `k8s/manifests/keycloak/ingress.yaml` serves `/idp` on `host: localhost`, like `ingress.yaml`, which `deploy.sh` applies and which sets no CSP. On the public host, `deploy.sh` (`PUBLIC_HOST`) gives the Keycloak ingress the same host as the frontend, and `www` only redirects to the apex. The old `ssl-ingress.yaml` (www and apex hosts, with a CSP) is retired, so no CSP is set on the public host either. A Keycloak on another origin must be added to `connect-src` and to a new `frame-src 'self' <keycloak-origin>` directive (none exists, so framing falls back to `default-src`), or sign-in, token renewal and the silent session restore are blocked |
| Backend `OIDC_REQUIRED` | `true`, so the backend refuses to start without an issuer (AUTH-5, PR #261, which sets it in `backend-deployment.yaml`) |
| `ENABLE_GRAPHQL_PLAYGROUND` | absent |

## Checks

Each check records its date, the image SHA and the result in the QA log (a tracking issue).
Coverage and alert commands come from the crawler coverage runbook,
`docs/monitoring/crawler-coverage-runbook.md` (DATA-10, PR #210).

1. **Coverage (criterion 2).** Start with an empty database and crawl every enabled source.
   Then run
   `kubectl -n econ-graph exec deploy/crawler-worker -- /app/crawler coverage --fail-under 95`.
   It must exit 0, and all six release sources (FRED, BLS, Census BDS, FHFA, BEA, WDI) must
   appear as rows. The command skips sources the scheduler doesn't fetch, so a missing row is a
   failure. Missing series are explained or ticketed. A search for a series with no data
   returns nothing.
2. **Freshness (criterion 3).** Leave the deployment alone for seven consecutive days.
   - Each day, `crawler coverage` shows `OVERDUE` 0 for every release source, and
     `CrawlerSourceNotRefreshed` has not fired.
   - Once, force a failure with the runbook's method:
     `/app/crawler enqueue --source FRED --series ECONGRAPH_QA_FORCED_FAILURE`.
     Then check that `CrawlerCrawlFailed` fires at Prometheus `/alerts`. This enqueues a bad job
     and touches no refresh, so it isn't a manual refresh step.
   - Run the forced failure after check 1's coverage reading, and afterwards confirm that
     `crawler coverage` and search show no `ECONGRAPH_QA_FORCED_FAILURE` series; deactivate it
     if a row exists.
   - Deactivating a series the source has discontinued (the runbook's
     `UPDATE economic_series SET is_active = FALSE`) is allowed and logged; it is not a refresh.
   - Nothing is restarted and no key is changed during the seven days.
3. **End to end (criterion 5).** Run the Release E2E suite, including its journey specs, in deployed-URL mode. Compared with the CI run:
   - latest points are checked against each source's cadence, not against fixture values;
   - the map check needs a value for every country the World Bank reports, with a floor of 150,
     for each of the three indicators.

   The live realm has Google sign-in and, for QA only, the two realm-local test users (the dev
   users alice and bob are never deployed). The suite signs in as those two: one annotates
   publicly and privately, and the other sees only the public annotation. The "Sign in" button
   shows on the deployed site. Check 4 covers the real Google sign-in by hand.
4. **Sign-in and tokens (criterion 6).** Call the backend directly, not through the frontend, and check:
   - `/playground` returns 404;
   - these calls are rejected: the annotation create mutation, a private
     `annotationsForSeries` read, and `/mcp`, each carrying
     - a token from another realm,
     - an HS256 token (for example one signed with the old `JWT_SECRET`),
     - a self-signed JWT;
   - a token from a real Google sign-in carries a top-level `roles` claim and is accepted;
   - CORS allows only the frontend origin.
5. **Leaked credentials (criterion 6).** The Google OAuth client secret and the Facebook token
   from the old `configmap.yaml` are revoked at the providers, and the Facebook app itself is
   deleted or disabled. They remain in git history, so removing them from the files is not
   enough. The repository's GitHub secret-scanning alerts are reviewed and each one is closed
   as revoked.
6. **Spot checks.** Pick one series from each source and compare its latest value and date with
   the source's own site.

## Exit

When all six checks pass and the maintainer agrees, `scripts/release/tag.sh` tags the tested commit on `release/v4.0` as `v4.0.0` and `train-1`, retagging the image digests QA ran. Every fix merged to the branch must have a forward-port PR into `main`, open or merged, before the tag.

A source that fails check 1, 2 or 6, or its per-source part of check 3, is dropped from `v4.0.0`
rather than holding the tag: a release can shrink but not grow. It is turned off by disabling its
`data_sources` row, which changes no image, so the seven-day clock keeps running. The release notes
say so. A failure elsewhere in check 3, or in check 4 or 5, holds the tag until it is fixed. A fix
that ships new backend or crawler-worker images restarts check 2's seven days. A frontend-only
fix does not.
