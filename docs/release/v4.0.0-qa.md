# Deployed release QA guide

Use this guide to gather evidence from an isolated release-candidate deployment. Fixture CI
checks recorded responses without live API keys; deployed QA checks live source coverage,
scheduled refresh, sign-in through Keycloak and Google, and behavior at the deployed URL.
Release scope, acceptance thresholds, observation periods and tag decisions belong in
[ECO-5](https://linear.app/econgraph/issue/ECO-5); target selection and live QA coordination
belong in [ECO-40](https://linear.app/econgraph/issue/ECO-40). The
[retained v4.0.0 QA acceptance policy](https://linear.app/econgraph/document/v400-qa-acceptance-policy-retained-from-the-repository-plan-749e00935349)
contains the source-removal and observation-clock rules; ECO-5 remains the release decision authority.

## Candidate prerequisites

Follow the [release process](../development/RELEASE_PROCESS.md) for the release branch,
image build and forward-port rules. Record the tested commit and image digests in the QA
tracking issue. Deploy the backend, crawler-worker and frontend images built by the
[Release Images workflow](../../.github/workflows/release.yml), tagged `sha-<commit>`. The
committed Kubernetes manifests run them under fixed names with `imagePullPolicy: Never`;
`scripts/deploy/load-release-images.sh` puts the candidate's images on the kind nodes under
those names, `verify-release-images.sh` checks the pods after `deploy.sh`, and
`rollback-release-images.sh` goes back (see [Release images on the kind cluster](../deployment/RELEASE_IMAGES.md)).
The load record holds the commit and digests to record.

Before collecting deployed evidence:

- Check the candidate's CI results and run [Release E2E](../../.github/workflows/release-e2e.yml)
  with GitHub's **Run workflow** button on the candidate commit. The workflow has path filters;
  a green [Core CI](../../.github/workflows/ci-core.yml) result alone does not establish that
  Release E2E ran.
- Run `scripts/check-release-features.sh` and
  `frontend/scripts/check-release-authenticity.mjs` with an empty allowlist. Check that
  `frontend/src/__tests__/graphqlOperationSkipList.ts` contains no operation used by a reachable route.
- Prepare the credentials and issuer configuration below before building and deploying the candidate.
- In the approved isolated QA realm, create the two test users defined in
  `config/keycloak/qa/`. The Compose path imports
  them through `docker-compose.qa-users.yml`; Kubernetes requires a QA-only `kcadm` or admin API
  step. No Kubernetes manifest may reference QA or dev users; the CI guard is
  `scripts/keycloak/check-no-dev-users-in-k8s.sh`. Direct grants are off, so the deployed suite
  signs in through the browser form.

## Select the QA target

Before any deployment or check, record the isolated QA cluster name, context, kubeconfig,
frontend URL, backend URL, Keycloak realm/issuer and app and data database identities in the
QA tracking issue. Confirm that these resources are separate from production, including
storage and the identity database. An empty data database is a fresh-crawl QA prerequisite,
not an instruction to clear an existing deployment. Do not run fresh-database checks or
create QA users in production.

The public deployment uses kind cluster `econ-graph` on `threadripper`; the host also runs
other clusters. For an isolated kind target, follow
[Testing on a scratch cluster](../deployment/HOST_STORAGE.md#testing-on-a-scratch-cluster).
Set `KIND_CLUSTER` to the approved QA cluster (never `econ-graph`),
`ECONGRAPH_SCRATCH_STORAGE` to its separate storage, `XDG_CACHE_HOME` to its scratch
cache and `ECONGRAPH_BACKUP_ROOT` to its separate backup directory as that procedure describes. Keep those settings for all deployment, backup and
migration commands below: the scripts otherwise default to production's cluster and paths.
Remove inherited `KUBECTL`, `KUBECONFIG`, `ECONGRAPH_KUBE_DIR` and
`KEYCLOAK_BACKUP_ROOT` overrides, or explicitly bind them to this same QA target and backup
location before using the operational scripts.

Use the selected cluster's own kubectl and kubeconfig for every QA command. After preparing
the target, define this helper with its recorded paths; plain `kubectl` on this host is a
MicroK8s wrapper and reaches a different cluster:

```bash
qa_kubectl() {
  KUBECONFIG="${QA_KUBECONFIG:?set the QA kubeconfig path}" \
    "${QA_KUBECTL:?set the QA kind kubectl path}" \
    --context "${QA_CONTEXT:?set the QA context}" -n econ-graph "$@"
}
```

The target needs the backend, frontend, crawler-worker, Postgres 18, Keycloak and Prometheus
loading `k8s/monitoring/prometheus-rules-crawler.yaml`. The Kubernetes path
(`scripts/deploy/deploy.sh` with `k8s/manifests`) supplies these components. It also applies
and waits for the chart API and does not deploy the admin frontend; account for the chart
API image in the deployment inventory.

### Public routing and production boundary

QA and test clusters remain unmarked and receive no production tunnel token. Deploy them
with `PUBLIC_HOST=` (empty), using the isolated access route recorded for QA. The non-empty
`PUBLIC_HOST` path is reserved for the marked cluster serving the public site. It renders
Keycloak's hostname and client origin, the backend issuer and CORS together with the
public HTTPRoutes. The localhost HTTPRoutes in
[`k8s/manifests/gateway/routes/httproutes.yaml`](../../k8s/manifests/gateway/routes/httproutes.yaml)
use the Gateway's HTTP listener. Public-host deployment adds an HTTPS listener and its
certificate, copies the routes onto that listener, and redirects public HTTP and `www`
requests to the HTTPS apex. The copies retain the frontend security headers. Use this
rendering rather than editing the committed localhost literals; see
[Gateway routing](../deployment/GATEWAY_ROUTING_TROUBLESHOOTING.md).

For production marker setup, recreation and removal, follow
[Production marker](../../k8s/README.md#production-marker). Mark only the public-serving
cluster before restoring into it, deploying with `PUBLIC_HOST`, or entering its tunnel token.
The marker and secret-creation scripts use the kind kubectl and kubeconfig by default;
unset an exported `KUBECONFIG` first to retain that behavior. Without the marker,
`create-secrets.sh` refuses the tunnel token. With an empty `PUBLIC_HOST`, deployment scales
cloudflared to 0; with a non-empty host on an unmarked cluster, it stops before applying
anything, leaving a previously running connector running. Every connector holding the
production token takes a share of public traffic. On a nonproduction cluster that previously
held it, `scripts/deploy/mark-production-cluster.sh --unmark` scales cloudflared to 0 and
offers to delete `cloudflare-tunnel` (type `delete` to confirm).

## Keycloak upgrade

Keycloak migrates its database schema the first time a new version starts, and an older
Keycloak can't run on the migrated schema. A deploy that changes the Keycloak image
(`k8s/manifests/keycloak/deployment.yaml`) on a cluster that already has a `keycloak`
database is therefore two steps, and the second runs only if the first succeeds:

```sh
scripts/deploy/backup-keycloak-db.sh && scripts/deploy/deploy.sh
```

`backup-keycloak-db.sh` uses the selected kind cluster's own kubectl and kubeconfig,
like `deploy.sh`, on context `kind-${KIND_CLUSTER}` unless `--context` says otherwise.
With `--dry-run`, it changes nothing.

The backup scales Keycloak to 0 and dumps the `keycloak` database from
`keycloak-postgres-0` into `$ECONGRAPH_BACKUP_ROOT/keycloak/<UTC time>/`
(defaulting to `~/econgraph-backups/keycloak/<UTC time>/` when the root is unset).
It restores that dump into a scratch database in the same Postgres, compares every table's
row count with the live database, drops the scratch database, and only then encrypts the
verified payload with the maintainer's public `BACKUP_AGE_RECIPIENT`.

`backup.tar.age` contains the dump, row counts and metadata recording the Keycloak image
that wrote the data and the cluster's kube-system namespace UID; the outer directory has a
ciphertext checksum and a `VERIFIED` timestamp. Encryption prerequisites and private tmpfs
staging are checked before downtime. See
[backup encryption and recovery](../deployment/BACKUPS.md#nightly-dumps). Nothing under
`~/econgraph-backups/keycloak/` is ever deleted by these scripts. The off-site wrapper
includes these verified encrypted bundles once its destination is configured; until then
copy the directory to another disk.

The `postgres-backup` CronJob and `scripts/deploy/backup-postgres-now.sh`
do not cover this database. The nightly `scripts/backup/dump-databases.sh` does dump it,
but with Keycloak running and checked by a read-through only, and its restore
(`scripts/backup/restore-dump.sh`) uses `pg_restore --clean`, which leaves behind the
tables a newer Keycloak added; take this dump before the upgrade.

Sign-in is down from the moment the backup scales Keycloak to 0 until the new Keycloak
pod is ready. Keycloak stays at 0 until `deploy.sh` applies its Deployment again; if
`deploy.sh` fails before that point, sign-in stays down. Then run `deploy.sh` again, or,
to bring back the version that is still in the Deployment, scale it up on the selected QA target:
`qa_kubectl scale deployment/keycloak --replicas=1`.

The Deployment uses the `Recreate` strategy, so the old version is stopped before the new
one migrates the database, and `deploy.sh` waits up to 900s for the new Keycloak to be
ready (and stops if it isn't) before the realm-import Job applies the realm to it. The
startup probe allows the same 900s for the start, migration included; a migration that
takes longer gets the pod restarted mid-migration, so on a much larger database raise
`failureThreshold` of the startup probe first.

## Keycloak rollback

To roll back Keycloak, use a verified dump taken with the older image. Never downgrade with
`kubectl rollout undo` or `kubectl set image`: the older version can't run on the migrated
database. Restore the pre-upgrade database before restarting the older version.

1. Put that image back in both `k8s/manifests/keycloak/deployment.yaml` and the
   `render-realm` init container of `k8s/manifests/keycloak/realm-import-job.yaml`. For
   the 26.8.1 upgrade that is `quay.io/keycloak/keycloak:26.7.4`; the dump's `VERIFIED`
   metadata names it as `keycloak_image` after interactive decryption.
2. Restore the dump. `scripts/deploy/restore-keycloak-db.sh --list` shows the verified
   dumps under the selected backup root. Pass the listed directory to
   `scripts/deploy/restore-keycloak-db.sh <verified-dump-directory>` to restore it. For an
   encrypted bundle it first prompts for the private identity path at an operator terminal
   and decrypts into disposable tmpfs. The script then shows whether the cluster is marked production and asks for the database name (`--dry-run` changes nothing). It refuses a dump taken on another
   cluster (another kube-system UID) unless given `--allow-other-cluster`. It:

   - scales Keycloak to 0 and takes a verified dump of the database as it is now,
     stopping if that fails;
   - restores the dump into a new database `keycloak_restore_<time>` in one transaction
     and checks every table's row count against the dump's; on any failure so far
     `keycloak` is untouched;
   - then, in one transaction, ends any connection to `keycloak`, renames it to
     `keycloak_pre_restore_<time>` and renames the restored database to `keycloak`.

   The script uses a fresh database because `pg_restore --clean` would leave behind the tables the newer version added. `keycloak_pre_restore_<time>` is
   kept; once Keycloak works again, drop it on the selected QA target:
   `qa_kubectl exec keycloak-postgres-0 -c postgres -- dropdb -U keycloak keycloak_pre_restore_<time>`.
3. Run `scripts/deploy/deploy.sh`.

Anything written to Keycloak after the dump (new accounts, Google-brokered sign-ups,
changed passwords) is lost from the live database; it stays in the dump the restore took
first and in `keycloak_pre_restore_<time>`.

## Observation-values migration

The deploy that brings in the observation-values migration (`20261025000100`, unconstrained
`NUMERIC` for observation values) locks `crawl_queue`, `data_points` and
`global_indicator_data` and gives up after about 10 seconds if other transactions hold them.
See the details in
[Deploying the migration](../technical/OBSERVATION_PRECISION_REFETCH.md#deploying-the-migration).
Schedule the entire deployment, from the precheck until the `crawler-migrate` Job completes,
outside the nightly `postgres-backup` window starting at 08:00 UTC. Then:

1. Immediately before `deploy.sh`, run `scripts/deploy/precheck-db-migration.sh --stop-crawler`
   (with `--dry-run` first). The precheck uses the selected kind cluster's kubectl and context,
   matching `deploy.sh`. It exits if a `postgres-backup` or `crawler-migrate` Job is running.
   Otherwise, it scales `crawler-worker` to 0 and waits for its pods to stop. It then lists
   transactions on the data database open for more than 5 seconds or idle in a transaction,
   and exits non-zero if any remain. It never ends sessions. If a check fails after the
   worker stops, it prints the command to scale the worker back up.
2. Run `scripts/deploy/deploy.sh`, whose `crawler-migrate` Job (`crawler migrate`) applies the
   migration before the backend and `crawler-worker.yaml` are applied; then confirm
   `20261025000100` is in the data database's `__diesel_schema_migrations`. If the Job fails
   on a lock or statement timeout (it tries twice), `deploy.sh` stops with the worker still
   stopped: find the session holding the tables (`precheck-db-migration.sh --dry-run`) and
   run `deploy.sh` again.
3. Check `crawler-worker` is back at 1 replica on the new image (`deploy.sh` applies it once
   `crawler-migrate` has completed).
4. Only then enqueue the full-history re-fetch (`scripts/deploy/refetch-full-history.sh`).

## Credentials and deploy config

Each credential lives in a Secret (created by `scripts/deploy/create-secrets.sh`) or
in the target's equivalent. No credential goes in the repo or in `k8s/manifests/configmap.yaml`.

| Credential | Used by | Notes |
|---|---|---|
| `FRED_API_KEY` | crawler | required |
| `BEA_API_KEY` | crawler | required |
| `CENSUS_API_KEY` | crawler | required for Census BDS |
| `BLS_API_KEY` | crawler | optional, but it raises the BLS limits the widened series list needs |
| Google OAuth client id and secret | Keycloak Google identity provider | replacement credentials after revocation of the leaked client (check 5), in Secret `econ-graph-keycloak`, keys `google-idp-client-id` and `google-idp-client-secret` |
| QA test users (two realm-local users with passwords) | Keycloak, QA only | see "Candidate prerequisites": created by a QA-only import behind a switch that is off by default, or by hand with `kcadm`; never in production. They let check 3 run the two-account annotation check automatically |
| Keycloak admin and database passwords | Keycloak | Secret `econ-graph-keycloak` |
| Database password | backend, crawler | |

`scripts/deploy/create-secrets.sh` sets the Google keys from `KEYCLOAK_GOOGLE_CLIENT_ID`
and `KEYCLOAK_GOOGLE_CLIENT_SECRET`. The realm-import Job applies them to the realm on every
`deploy.sh`, so a change made only in the Keycloak admin console is overwritten by the next
deploy. Change the Secret and deploy again. Keycloak enables the Google sign-in button only
when both keys are set.

FHFA and the World Bank need no key.

Use the settings for the recorded QA access route. The `PUBLIC_HOST` values below describe
the public production route; an unmarked QA cluster keeps `PUBLIC_HOST=` and needs an issuer
reachable through its isolated route. Verify the frontend redirect origin and backend issuer
together before sign-in checks.

| Setting | Value |
|---|---|
| `vars.VITE_OIDC_ISSUER` (repository variable, frontend build) | `/idp/realms/econ-graph` for Keycloak on the frontend origin, or its absolute issuer URL. The Kubernetes path serves Keycloak under `KC_HTTP_RELATIVE_PATH=/idp`. If unset, the build hides sign-in, so it must be set before the release candidate build |
| `vars.VITE_OIDC_CLIENT_ID` | only if the client isn't `econ-graph-web` (the default) |
| Backend `OIDC_ISSUER` | Keycloak's absolute issuer, equal to the frontend issuer after resolving any path against the frontend origin. The backend compares `iss` exactly. `PUBLIC_HOST` renders `https://<host>/idp/realms/econ-graph`; without it the manifest uses `http://localhost/idp/realms/econ-graph` |
| Backend `OIDC_JWKS_URL` | keep the in-cluster `keycloak-service` URL from `backend-deployment.yaml`, so the backend fetches signing keys without going through the public Gateway route. Clear it only if the backend can reach the public issuer URL |
| Backend `OIDC_AUDIENCE` | `econ-graph-api`, as the manifest already sets it (also the default) |
| `CORS_ORIGIN` (configmap, feeds `CORS_ALLOWED_ORIGINS`) | the allowed frontend origins. `PUBLIC_HOST` prepends the public origin and preserves the localhost origins already configured |
| Keycloak `KC_HOSTNAME` | the public Keycloak URL, including `/idp` on the Kubernetes path |
| Keycloak `KC_HOSTNAME_ADMIN` | the admin access URL, separate from the public realm route. The manifest uses `http://localhost:18080/idp` for a port-forward; the Gateway does not expose `/idp/admin` |
| Keycloak `KC_WEB_BASE_URL` | the deployed frontend origin, which must also appear in `CORS_ORIGIN`: the realm's `econ-graph-web` client takes its root URL, redirect URIs and web origins from it |
| Google client's redirect URI | `https://<keycloak-host>/idp/realms/econ-graph/broker/google/endpoint` |
| Keycloak route | The `econ-graph-idp` HTTPRoute in `k8s/manifests/gateway/routes/httproutes.yaml` serves the realm and login assets under `/idp` on `localhost`. `PUBLIC_HOST` adds a public HTTPS copy; the admin console and master realm are not routed |
| Backend `OIDC_REQUIRED` | `true` in `backend-deployment.yaml`, so the backend refuses to start without an issuer |
| `ENABLE_GRAPHQL_PLAYGROUND` | absent |

The frontend HTTPRoute sets a Content-Security-Policy (CSP) with
`connect-src 'self' wss:` and `default-src 'self'`. Same-origin Keycloak under `/idp`
fits that policy. Before using a separate Keycloak origin, add it to `connect-src`
for sign-in and token renewal and add `frame-src 'self' <keycloak-origin>` for silent
session restore. With no `frame-src`, framing falls back to `child-src`, then
`default-src`; check the policy on the selected QA access route as well.

General frontend responses deny framing with `X-Frame-Options: DENY` and
`frame-ancestors 'none'`. The exact `/silent-callback.html` route instead sets
`X-Frame-Options: SAMEORIGIN` and `frame-ancestors 'self'` so the app can load its silent
sign-in callback in a hidden iframe. Preserve that exception when changing headers.
Public-host rendering copies both policies to the public HTTPS routes.

## Checks

For each check, record the date, image SHA, target and result in the QA tracking issue.
Coverage and alert procedures are in the
[crawler coverage runbook](../monitoring/crawler-coverage-runbook.md). Use `qa_kubectl`
in place of its unqualified kubectl commands to keep them on the selected QA target.

1. **Coverage.** On the isolated QA data database prepared above, crawl every enabled source.
   Then run
   `qa_kubectl exec deploy/crawler-worker -- /app/crawler coverage --fail-under 95`.
   Record the exit status and check the rows against the enabled sources in the agreed QA
   scope (FRED, BLS, Census BDS, FHFA, BEA and WDI for a six-source run). The command omits
   disabled sources and sources the scheduler does not fetch; exit 0 alone does not establish
   coverage for an omitted source. Explain or ticket missing series. Check that searching
   for a series with no data returns nothing.
2. **Freshness.** Leave the deployment running scheduled refresh for the observation period
   specified in the release ticket. For a seven-day observation:

   - Each day, `crawler coverage` shows `OVERDUE` 0 for every release source, and
     `CrawlerSourceNotRefreshed` has not fired.
   - Once, force a failure with the runbook's method:
     `/app/crawler enqueue --source FRED --series ECONGRAPH_QA_FORCED_FAILURE`.
     Then check that `CrawlerCrawlFailed` fires at Prometheus `/alerts`. This enqueues a bad job
     and touches no refresh, so it isn't a manual refresh step.
   - Run the forced failure after check 1's coverage reading, and afterwards confirm that
     `crawler coverage` and search show no `ECONGRAPH_QA_FORCED_FAILURE` series; deactivate it
     if a row exists.
   - Deactivating a series the source has discontinued (the runbook's
     `UPDATE economic_series SET is_active = FALSE`) is allowed and logged; it is not a refresh.
   - Nothing is restarted and no key is changed during the seven days.
3. **End to end.** Follow [Against a deployed build](../../frontend/tests/e2e/release/README.md#against-a-deployed-build-rel-qa-check-3).
   Run Playwright directly from `frontend`, using `npx playwright test --config=playwright.release.config.ts`;
   `scripts/release-e2e.sh` starts the fixture stack. Set `RELEASE_BASE_URL`,
   `RELEASE_OIDC_ISSUER`, `RELEASE_QA_USER1_PASSWORD` and `RELEASE_QA_USER2_PASSWORD`
   through the QA environment. Playwright starts no local web server and needs no database URL.
   Include the journey and auth specs; `RELEASE_SKIP_AUTH=1` omits sign-in evidence.

   The journey and six-source sweep check latest points against source cadences in deployed
   mode. The map tests have different boundaries: `world-map.spec.ts` still asserts exact
   `SEEDED_WDI` values and country counts, `world-map-every-country.spec.ts` skips deployed
   mode, and the mocked map specs use intercepted responses. Their results cannot establish
   live country coverage. Preserve the raw suite result and identify fixture-bound failures
   separately from live regressions.

   Collect live map evidence separately at `/global`. Select each of GDP per capita
   (`NY.GDP.PCAP.CD`), population (`SP.POP.TOTL`) and inflation (`FP.CPI.TOTL.ZG`). For each,
   save the browser's `GetMapCrossSection` response and open **Values as a table** to record
   the country, value and date rows. Compare those rows with the World Bank's latest
   non-null country observations for the same indicator, following the
   [World Bank fetch and pagination procedure](../data-sources/world-bank.md#what-we-fetch-today).
   Keep the upstream response and retrieval date with the evidence. Exclude regional aggregates from the country comparison;
   record missing countries and count countries with values against the release ticket's
   requirement. Check each corresponding map outline and tooltip against the table. Countries
   without an ISO numeric code cannot be drawn; record their table values separately rather
   than counting them as colored outlines. Repeat after each indicator switch. The
   [map data hook](../../frontend/src/components/global/hooks/useWorldMapData.ts) defines the
   queries used by the page; this is manual live evidence, not an automated map assertion.

   The QA realm has Google sign-in and the two QA-only realm users; dev users are never
   deployed. The signed-in suite checks that one account can annotate publicly and privately
   and that the other sees only the public annotation. Check that the deployed **Sign in**
   button appears. Check 4 covers Google sign-in manually.
4. **Sign-in and tokens.** Call the backend directly, not through the frontend, and check:

   - `/playground` returns 404;
   - these calls are rejected: the annotation create mutation, a private
     `annotationsForSeries` read, and `/mcp`, each carrying

     - a token from another realm,
     - an HS256 token (for example one signed with the old `JWT_SECRET`),
     - a self-signed JWT;
   - a token from a real Google sign-in carries a top-level `roles` claim and is accepted;
   - CORS accepts the configured frontend origins and rejects an unrelated origin. Record the
     actual allowlist: public-host rendering preserves localhost origins, so it does not
     establish a public-frontend-only policy. Evaluate any stricter release requirement in
     the release tracking issue.
5. **Leaked credentials.** The Google OAuth client secret and the Facebook token
   from the old `configmap.yaml` are revoked at the providers, and the Facebook app itself is
   deleted or disabled. They remain in git history, so removing them from the files is not
   enough. The repository's GitHub secret-scanning alerts are reviewed and each one is closed
   as revoked.
6. **Spot checks.** Pick one series from each source and compare its latest value and date with
   the source's own site.

## Evaluate the evidence

Record each check's result, source-specific failures, skipped tests and manual evidence in
the QA issue. Apply the
[retained acceptance policy](https://linear.app/econgraph/document/v400-qa-acceptance-policy-retained-from-the-repository-plan-749e00935349),
including its source-removal and observation-clock reset rules, with ECO-5 as the decision
authority before following the [tagging procedure](../development/RELEASE_PROCESS.md). A database source toggle
does not change the candidate image or the Playwright test set: the six-source sweep always
iterates over `SWEPT_SOURCES`. If the release scope excludes a source, record the affected
coverage rows and test failures explicitly and obtain the release decision in the tracking
issue; do not describe the full suite as passing or assume a disabled row filters its tests.
