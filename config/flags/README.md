# Feature flags

The flag files for EconGraph, in [flagd](https://flagd.dev)'s flag format. The
design, including which kinds of flag exist and when not to use one, is in
the Linear [Feature flags](https://linear.app/econgraph/project/feature-flags-bc727011a0f7)
project.

| File | What it holds |
|---|---|
| `flags.flagd.json` | Every flag. Each flag's `defaultVariant` is its **release** value |
| `dev.flagd.json` | Overrides for development builds and local runs, and nothing else |
| `schema/` | flagd's JSON schema, vendored so the check needs no network |

A build profile is `release` or `dev`. The `release` profile is
`flags.flagd.json` alone. For the `dev` profile, each entry in `dev.flagd.json`
replaces the entire matching entry from `flags.flagd.json`, following flagd's
rule for several sources. The generator takes each flag's `kind` from the base
definition, so dev overrides do not need metadata.

`node scripts/flags-merge` applies that rule once and writes the resolved values
to `frontend/flags/<profile>.json` and `backend/flags/<profile>.json`, because
the frontend and backend Docker builds can't see `config/flags`. Vite and the
Rust build scripts read the generated file for their selected profile, so
neither re-implements the merge. The generated files are committed, and CI
fails when they are stale. Their shape, with one flag shown:

```json
{
  "$comment": "Generated by scripts/flags-merge ...",
  "profile": "release",
  "flags": {
    "mcp": { "kind": "build", "value": false }
  }
}
```

A flag with `"state": "DISABLED"` is left out, which flagd treats as absent.

Each build flag's key maps to a name in code: for example, `world_map` becomes
`__FLAGS__.world_map` in the frontend and `cfg(flag_world_map)` in Rust. See
[frontend build flags](../../frontend/docs/build-flags.md) for the import pattern
that lets Vite remove flagged-off code.

## How the backend reads it

Each crate using build flags must call `econ_graph_flags_build::emit()` from its
own `build.rs`; the emitted cfgs apply only to that crate. Both
[`econ-graph-backend`](../../backend/crates/econ-graph-backend/build.rs) and
[`econ-graph-crawler`](../../backend/crates/econ-graph-crawler/build.rs) do this.
The [shared helper](../../backend/crates/econ-graph-flags-build/src/lib.rs) reads
`FLAGS_PROFILE` (`release` when unset, or `dev`), finds
`backend/flags/<profile>.json`, and emits `cargo::rustc-cfg=flag_<key>` for each
enabled build flag. A crate can then gate a module or route with, for example,
`#[cfg(flag_world_map)]`.

[`backend/.cargo/config.toml`](../../backend/.cargo/config.toml) sets
`FLAGS_PROFILE=dev` for local builds and tests; an exported `FLAGS_PROFILE` wins
over it. [`backend/Dockerfile`](../../backend/Dockerfile) does not copy that
configuration file and defaults to `FLAGS_PROFILE=release`. Pass
`--build-arg FLAGS_PROFILE=dev` to build a development image. `cargo build --release`
selects Cargo's own release profile (optimizations) and has no effect on
`FLAGS_PROFILE`.

For a flag gating a whole route, such as `mcp`, put the route's module behind
`#[cfg(flag_<key>)]`. Supply a `#[cfg(not(flag_<key>))]` stand-in with the same
signature that always returns 404, so the code wiring up routes needs no cfg.
When adding a field gate to a larger GraphQL type, compose two root variants
selected by opposite cfg conditions. The enabled root includes both the
feature's fields and the shared fields; the disabled root retains the shared
fields and excludes the feature's fields.

## Adding a flag

1. Add it to `flags.flagd.json`, with a snake_case key, `"state": "ENABLED"`,
   boolean `on`/`off` variants, and the release value as `defaultVariant`: off
   for build and preview flags, on for an ops kill switch.
2. Give it `metadata`:

   | Key | Required for | Value |
   |---|---|---|
   | `kind` | every flag | `build` (unfinished code compiled out of release builds), `preview` (works end to end, shown to some people first), `ops` (kill switch), or `experiment` |
   | `owner` | every flag | The Linear issue that owns it, such as `ECO-NNN`, or a Linear project URL |
   | `stage` | `preview` only | `alpha` or `beta` |
   | `remove_by` | `build` and `preview` | `"train N"` or `"unscheduled"`. CI fails once tag `train-N` (or one with a higher N) exists and the flag is still here |

   No other metadata keys are allowed, so a typo fails the check. `ops` flags
   are long-lived and take no `remove_by`; an `experiment` flag may carry one.
   `build` flags are folded into the bundle at build time, so they have boolean
   variants and no `targeting`.
3. To change its value for development, add an override to `dev.flagd.json`:
   the same `state` and `variants`, a different `defaultVariant`, and nothing
   else. Leave it out when development should match release, which is the
   case for code parked behind a flag that is off everywhere.
4. Check it and regenerate the per-profile files, then commit them too:

   ```sh
   node scripts/check-flags
   node scripts/flags-merge
   ```

Example:

```json
"world_map": {
  "state": "ENABLED",
  "variants": { "on": true, "off": false },
  "defaultVariant": "off",
  "metadata": {
    "kind": "build",
    "owner": "ECO-NNN",
    "remove_by": "train 1"
  }
}
```

A completed train is marked by `train-N`. Product releases use
`scripts/release/tag.sh` to push that marker with their version tag. Train 3 is
a development milestone: its separate [milestone helper](../../scripts/release/tag_milestone.py)
pushes only `train-3`, after acceptance on main. Both kinds of completed train
count for expiry. From then on the check fails for every flag still marked
`remove_by: "train N"` or lower. Before pushing a marker,
`node scripts/check-flags --shipped-train N` lists the flags that must be removed first.

## Removing a flag

Delete it from both files in the PR that finishes or replaces the feature,
run `node scripts/flags-merge`, and remove the code paths for its other value.

## The seeded flags

- `build_canary` (build, off in release, on in dev, `remove_by: unscheduled`)
  guards a module with a unique marker string, so CI can prove a release bundle
  leaves flagged-off code out. It is one of two permanent build flags (see
  `static_catalogs` below), kept rather than removed because it's a standing
  check, not unfinished work.
- `mcp` (build, off in release, on in dev, `remove_by: train 7`, owner ECO-123,
  the issue that gates `/mcp` behind the flag) compiles `/mcp` out of release
  builds.
- `static_catalogs` (build, off in release, on in dev, `remove_by: unscheduled`,
  owner ECO-142) registers `econ-graph-crawler`'s ten hardcoded dev-only source
  catalogs (BOC, BOE, BOJ, ECB, ILO, OECD, RBA, SNB, UN_STATS, WTO). Like
  `build_canary`, it is permanent: these catalogs are a development convenience,
  so there is no release deadline for removing the flag.

## Updating the vendored schema

[`schema/flags.json`](schema/flags.json) and
[`schema/targeting.json`](schema/targeting.json) are copied unchanged from
[open-feature/flagd-schemas](https://github.com/open-feature/flagd-schemas)
at tag `json/json-schema-v0.2.15` (Apache-2.0, see [the license](schema/LICENSE)). To update,
copy both files from a newer tag's `json/` directory and run the check. The
check's validator supports only the JSON Schema keywords these files use, and
fails loudly on any other.

## Train 3 deadline audit

Train 3 establishes shared development contracts without shipping unfinished
features or changing production flag values. The deadlines follow the planned
feature completion, rather than product version numbers:

| Flag | Deadline | Reason |
|---|---|---|
| `mcp` | Train 7 | Workspace and machine access complete in Train 7. |
| `global_analysis_tabs` | Train 8 | Comparative research completes in Train 8. |
| `financial_components` | Train 5 | The SEC financial UI/demo belongs to Train 5 company research; completion replaces the unfinished financial surface. |
| `technical_analysis` | Unscheduled | No committed feature completion train yet. |
| `build_canary`, `static_catalogs` | Unscheduled | Permanent development/build checks described above. |

Only deadline metadata changes at this cut. The generated development and release
profiles retain exactly the same values. Product versions remain Train 4 v4.2.0,
Train 5 v4.3.0, Train 6 v4.4.0, Train 7 v4.5.0, Train 8 v4.6.0 and Train 9 v4.7.0.
